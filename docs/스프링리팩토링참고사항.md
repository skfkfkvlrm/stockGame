# SchoolStock 스프링 부트 3.x & 자바 21 종합 리팩토링 가이드라인

본 문서는 초등 모의투자 시스템(**SchoolStock**) 프로젝트의 웹 애플리케이션 아키텍처를 순수 자바 서블릿/JSP 및 Native MyBatis 환경에서 **Java 21** 및 **Spring Boot 3.x** 기반의 최신 레이어드 아키텍처(Layered Architecture)로 전면 마이그레이션할 때 준수해야 하는 **최종 통합 개발 조약**입니다.

인텔리제이(IntelliJ) 환경 내의 **Gemini Code Assist**는 레거시 프로젝트 소스코드(`src/com/school/stockGame/`)를 스프링 컴포넌트로 리팩토링하거나 신규 마이그레이션 코드를 제안할 때 본 문서에 명시된 아키텍처 변환 규칙과 데이터베이스 방어 조약을 철저히 인지하고 반영해야 합니다.

## 1. 런타임 인프라 및 환경 제약조건

### [규칙 1-A] Jakarta EE 10 전면 도입 (javax.* 패키지 영구 폐기)
* Spring Boot 3.x 생태계 및 내장 톰캣(Tomcat 10 사양) 빌드 규칙에 따라 기존 레거시 서블릿 패키지인 `javax.servlet.*`를 더 이상 매핑할 수 없습니다.
* 웹 및 컨트롤러 계층의 모든 서블릿/필터 참조 코드를 **`jakarta.servlet.*`** 명명 공간(Namespace)으로 전면 교체해야 합니다.

### [규칙 1-B] 데이터베이스 커넥션 풀 현대화 (HikariCP 이관)
* 수동으로 싱글톤 구조를 구현해 관리하던 구형 팩토리 클래스 `DBCPMybatis.java` 및 `DBCP.java` 코드를 전면 폐기합니다.
* 빌드 스크립트(build.gradle / pom.xml)에 `mybatis-spring-boot-starter` 의존성을 주입하고, 스프링 부트의 기본 고성능 커넥션 풀인 **HikariCP**에게 데이터베이스 세션 및 커넥션 라이프사이클 관리를 완전히 위임합니다.

### [규칙 1-C] 글로벌 인코딩 및 빌드 표준화
* 모든 자바 소스코드 파일, Properties 설정, XML 파일 및 뷰 템플릿의 상단 선언부는 인코딩 파편화로 인한 컴파일 및 배포 크래시를 원천 차단하기 위해 무조건 **`UTF-8`**로 통일합니다.

### [규칙 1-D] JSP 호환성을 위한 빌드 및 패키징 조약 (JAR 가동 불가)
* 스프링 부트 3.x 환경은 임베디드 톰캣 구동 시 기본적으로 내장 JSP 렌더링을 완전히 지원하지 않습니다. 
* 기존 화면 템플릿을 수정 없이 그대로 유지해야 하므로, 본 프로젝트는 반드시 빌드 가이드에서 **`WAR (Web Application Archive)` 패키징 형식을 강제**하며, `tomcat-embed-jasper` 및 `jakarta.servlet.jsp.jstl` 스타터 종속성을 필수 보존해야 합니다.

## 2. Spring MVC 프리젠테이션 계층 컨버전 조약

기존 단일 진입점 구조(`FrontControllerServlet` 및 `ActionFactory`)를 제거하고 URL 매핑 기반의 Spring 컴포넌트 아키텍처로 세분화하여 관심사를 격리합니다.

```
[Boundary / Client (JSP/AJAX)]
              │
              ▼
[@Controller / @RestController] (Presentation Layer) ➔ 세션 파라미터 주입 및 선언적 검증
              │
              ▼
     [@Service] (Business Logic Layer) ➔ 비즈니스 유효성 검증 및 트랜잭션 경계
              │
              ▼
      [@Mapper Interface] (Data Access Layer) ➔ XML 매퍼와 일대일 컴파일 결합
```

### [규칙 2-A] Controller 성격 분리 및 PRG 패턴 강제
* **`@Controller` (전통 MVC SSR):** 내 자산 화면(`MyAssetsUIAction`), 주식 목록(`StockListUI`), 뉴스 목록(`NewsUIAction`)과 같이 JSP 및 Thymeleaf 뷰 템플릿 경로를 포워딩하는 컨트롤러에 선언합니다.
    * **중복 등록 방지 조약:** 매수 주문(`StockBuyAction`), 매도 주문(`StockSellAction`), 회원 등록 및 로그인 처리 같이 데이터베이스 상태를 변경하는 `POST` 요청 컨트롤러 메서드는 화면 새로고침에 의한 데이터 중복 적재를 차단하기 위해 무조건 **PRG(Post-Redirect-Get) 패턴**을 준수하는 리다이렉트 구문 (`return "redirect:/main";`)을 반환해야 합니다.
* **`@RestController` (비동기 REST API):** 실시간 현재가 업데이트(`StockPriceAjax`), 가용 호가 현황 확인(`StockOrderStatusAcion`), 아이디 중복 체크(`IdCheckAction`) 등 비동기 요청을 전담하는 컨트롤러에 선언합니다.
    * 레거시 코드 내부의 수동 JSON 문자열 조립 코드 및 구형 `Gson` 파싱 로직을 전면 삭제하고, 자바 객체(또는 Record DTO)를 즉시 리턴하여 스프링의 `Jackson2ObjectMapper` 메커니즘이 자동으로 응답 스트림에 JSON 형태로 직렬화하도록 유도합니다.

### [규칙 2-B] 어노테이션 기반 세션 바인딩 현대화
* 기존 레거시 Action 파일 내부에서 `request.getSession().getAttribute("student_id")` 문장으로 세션 속성을 직접 제어하던 하드코딩을 전면 금지합니다.
* 컨트롤러 메서드 파라미터 상에 **`@SessionAttribute(name = "student_id", required = false)`** 규칙을 적용하여 인프라 레벨에서 세션 변수가 동적으로 바인딩되도록 전면 고도화합니다.

### [규칙 2-C] Jakarta Bean Validation을 통한 입력 검증 선언화
* 숫자로 변환될 매수/매도 수량 인자가 비어 들어오거나(`""`), 마이너스 수량 훼손 값이 들어올 때 발생하던 `NumberFormatException` 리스크를 방어하기 위해 비즈니스 DTO 클래스에 선언적 검증 속성을 매핑합니다.
* 컨트롤러 진입 파라미터 상에 **`@Valid`** 또는 **`@Validated`** 선언을 필수 인입하고, 수량 DTO 객체 내부에 `@Positive(message = "수량은 1주 이상이어야 합니다.")` 혹은 정수형 `@Min(1)` 속성을 강제하여 에러 핸들러 단에서 자동 필터링되도록 아키텍처 규칙을 수립합니다.

## 3. 비즈니스 로직 및 전역 예외 제어 계층화

### [규칙 3-A] 비즈니스 로직의 서비스 레이어(@Service) 격리
* 레거시 Action 클래스 내부에서 request 파라미터를 꺼내 직접 연산하거나 검증하던 비즈니스 로직(가용 자산 확인, 손익 계산 공식, 회원 가입 조건 유효성 체크 등)을 프리젠테이션 계층에서 분리하여 전용 **`@Service`** 컴포넌트로 이관합니다.

### [규칙 3-B] 글로벌 예외 처리기 (@RestControllerAdvice) 정립 및 눈높이 설계
* **리스크 요인:** 주식 매수 중 잔고 부족 예외가 발생하거나, 데이터베이스 다운 등의 치명적 결함이 발생할 때 화면 레이어에 하얀색 Tomcat 500 내장 에러 페이지가 노출되면 사용자인 초등학생들의 시스템 이탈율이 급격히 증가합니다.
* **방어 전략:** 프로젝트 전역에 컨트롤러 관통 프록시 예외 처리기인 **`@RestControllerAdvice` 및 `@ControllerAdvice` 컴포넌트를 필수 신설**합니다.
* `SQLException`, `DataAccessException`, `ValidationException` 등 임계 영역 예외를 중앙 집중식으로 캐치하여 비동기 응답 시에는 정형화된 공통 에러 응답 객체(`ErrorResponse`) JSON 구조를 반환하고, 화면 이동 요청 시에는 팝업 레이어나 커스텀 에러 모달로 우회 가동하도록 웹 예외 트래킹 파이프라인을 정립해야 합니다.

## 4. 영속성(MyBatis) 및 Oracle DB 데이터 매핑 방어 조약 (★기존 비즈니스 보존)

스프링 부트 환경으로 마이그레이션하더라도 Oracle DB와의 MyBatis 연동 시 데이터 무결성을 보장하기 위해 아래 3대 매퍼/SQL 튜닝 가이드를 절대적으로 유지해야 합니다.

### [규칙 4-A] Oracle Map 반환 시 Key 대소문자 불일치 차단 (소문자 쌍따옴표 별칭 가이드)
* **리스크 요인:** MyBatis 환경에서 `resultType="map"` 구조로 데이터를 조회하여 자바의 `Map<String, Object>` 형태로 프리젠테이션 레이어에 전달할 때, 오라클 드라이버는 명시적인 소문자 별칭이 가공되지 않으면 Map의 Key 명칭을 강제로 **전체 대문자**(`NAME` ➔ `NAME`, `stock_no` ➔ `STOCK_NO`)로 반환합니다. 이로 인해 기존 프론트엔드 자바스크립트나 JSP EL 문법에서 소문자 Key 이름(`map.name` 또는 `map.get("name")`)으로 값을 읽으려 할 때 `NullPointerException`이 연쇄 발생하게 됩니다.
* **방어 전략:** 스프링 부트 환경의 매퍼 XML 파일에서도 `resultType="map"`을 반환하는 모든 `SELECT` 컬럼문 및 통계 가공 수식 뒤에는 반드시 **쌍따옴표 기호(`""`)를 사용해 소문자 및 카멜케이스 별칭(Alias)을 확실히 고정**해 기존 Action/View 소스코드와의 호환성을 완벽히 사수해야 합니다.

```xml
<!-- [올바른 지침] 쌍따옴표 별칭을 강제 적용하여 소문자 'name', 'stockNo' Key를 확정 바인딩 -->
<select id="getStockDetail" resultType="map">
    SELECT 
        name AS "name", 
        stock_no AS "stockNo" 
    FROM stocks 
    WHERE stock_no = #{stockNo}
</select>
```

### [규칙 4-B] 기본형(Primitive Type) int 언박싱 크래시 차단 (SQL 단 NVL 안전장치 가이드)
* **리스크 요인:** 특정 학생의 전체 주식 평가 손익(`SUM(stock_profit)`)이나 보유 주식 수량, 포인트 획득 통계 등을 단일 정수형 결과값으로 받아올 때, 만약 신규 가입자이거나 거래 내역이 존재하지 않아 테이블 내부가 비어있으면 MyBatis 프레임워크는 자바 단에 `null` 데이터를 반환합니다. 이 결과가 매퍼 인터페이스에 정의된 기본형 리턴 타입인 `int` 변수에 바인딩(오토 언박싱)되는 런타임 순간에 `NullPointerException`이 발생해 웹 컨텍스트 전체가 다운되는 치명적인 크래시가 발생합니다.
* **방어 전략:** 수치, 수량, 포인트 등을 조회하는 모든 산술 연산 및 집계(`SUM`, `AVG`, `COUNT` 등) SQL  쿼리문에는 오라클 표준 함수인 **`NVL()`** 또는 **`COALESCE()`** 구문을 필수 배치하여 데이터 부재 시에도 런타임 안정성을 보장하는 정수 `0` 또는 baseline 가격이 확정 반환되도록 제어해야 합니다.

```xml
<!-- [올바른 지침] NVL을 배치하여 어떠한 조건에서도 확실한 정수 0을 반환하도록 제어 -->
<select id="getTotalProfit" resultType="int">
    SELECT NVL(SUM(stock_profit), 0) FROM orders WHERE student_id = #{studentId}
</select>
```

### [규칙 4-C] 스네이크케이스 전역 자동 매핑 활성화
* 데이터베이스의 Snake_case 명명 규칙(예: `student_id`)과 자바 엔티티/DTO 객체의 CamelCase 명명 규칙(예: `studentId`)이 매퍼 XML 내의 별도 ResultMap 매핑 선언 없이도 자연스럽게 주입되도록 전역 설정 파일(`application.properties`)에 설정을 필수로 적용해야 합니다.
```properties
mybatis.configuration.map-underscore-to-camel-case=true
```

### [규칙 4-D] 레거시 구체 DAO 클래스 폐기 및 @Mapper 인터페이스 결합
* 기존 구체 구현 클래스 파일(`StockDetailDAOMybatis.java` 등) 내부에서 자원 관리를 위해 작성되었던 복잡한 `try-finally`, `session.close()` 연산 및 오타 리스크가 존재하는 문자열 기반 호출 구문을 **전면 삭제**합니다.
* 표준인 자바 인터페이스 파일 상단에 **`@Mapper`** 애노테이션을 부여하여 스프링 빈(Bean)으로 등록되도록 격상시키고, 메서드 명칭과 매퍼 XML 내의 태그 ID가 일대일 컴파일 결합을 이루도록 재편합니다.

## 5. 선언적 트랜잭션(@Transactional) 및 무결성 보장 (ORA-02291 에러 방어)

* **수동 제어 코드 전면 폐기:** 레거시 코드 내부에서 자원 관리를 위해 복잡하게 구현했던 `session.commit()`, `session.rollback()` 구문은 중복 보일러플레이트 코드를 유발하고 가독성을 저해하므로 무조건 전면 삭제합니다.
* **선언적 트랜잭션 경계 설정:** 예수금 차감 후 주문 요청을 삽입하는 매수/매도 프로세스나 포인트 차감 후 쿠폰 소유권을 적재하는 복합 수정 시나리오는 프리젠테이션 계층이 아닌 **`@Service` 레이어의 핵심 메서드 레벨에 `@Transactional` 애노테이션을 선언**하여 트랜잭션 경계를 지정합니다.
* **원자성 및 참조 무결성(ORA-02291) 제어:** 서비스 레이어 내부에서 예외(`RuntimeException`)가 발생하거나 가용 포인트 검증 실패 시 예외를 외부로 전파하여 스프링 AOP 프록시 메커니즘이 원자적(Atomicity) 롤백을 수행하게 만듭니다. 이를 통해 일부 쿼리만 오라클 디스크에 단독 반영되어 데이터 참조 무결성이 깨지거나 외래키 제약조건 위반 오류(`ORA-02291: parent key not found`)가 터져 나오는 임계 리스크를 근본적으로 차단합니다.

## 6. 자바 21 최신 문법 및 불변 데이터 레이어 도입

### [규칙 6-A] Java 21 record 문법을 활용한 불변 DTO/VO 전면 재편
* 데이터를 전송하거나 컨트롤러에서 응답으로 내려보내는 모든 바인딩 목적성 데이터 객체(VO 및 DTO)는 Java 21의 **`record`** 키워드로 과감하게 리팩토링합니다.
* 기존 클래스 기반 객체들에서 빈번하게 유실되거나 장황한 코드를 형성하던 Getter/Setter 구조를 제거하고 기본 생성자 누락 오류를 완전히 원천 차단합니다. MyBatis 3.5 사양 이상부터는 Java Record 객체의 생성자 파라미터 매핑을 네이티브하게 완벽 지원합니다.

```java
// Java 21 불변 데이터 Record 선언 가이드 양식
public record OrderDTO(
    int orderNo,
    String content,
    int price,
    int amount,
    String state,
    String studentId,
    int stockNo
) {}
```

### [규칙 6-B] Pattern Matching 문법을 활용한 조건 분기 가독성 개선
* 주식 매매 엔진의 호가 매칭 상태 판별, 회원 가입 입력 필드 스캔, 턴(Turn) 제어 로직 분기 처리 시 기존의 지저분한 `if-else` 블록 대신 Java 21의 **Pattern Matching for switch** 및 **Switch Expressions**를 과감하게 주입하여 확장 유연성을 보장하고 휴먼 컴파일러 결함 발생률을 최소화합니다.

```java
// Java 21 Switch Expressions 적용 예시 가이드
String statusMessage = switch (orderState) {
    case "대기" -> "주문이 접수되어 체결을 기다리고 있습니다.";
    case "체결" -> "거래가 성공적으로 완료되었습니다.";
    case "취소" -> "사용자에 의해 주문이 취소되었습니다.";
    default -> throw new IllegalArgumentException("올바르지 않은 주문 상태 유형: " + orderState);
};
```
